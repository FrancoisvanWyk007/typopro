# Typopro

A browser proof of concept for a rhythm-controlled typing music game. A song plays continuously and the vocals play on their own. Each half of the keyboard drives one instrument: play the left-hand keys well and the bass comes up in the mix, play the right-hand keys well and the keys come up. Miss, and they fade toward silence.

Two modes, chosen on the start card (**One sentence** is the default):

- **Two lanes**: each hand types its own word sequence at the same time ("brave waves…" on the left, "jolly moon…" on the right). This is harder, because both run at once.
- **One sentence**: one ordinary sentence typed in order, one letter per beat, never two keys at once. Each letter's side of the keyboard decides which instrument it plays. There are no falling keys: the sentence scrolls through a text cursor, and each letter reaches the cursor on its beat, so you read words ahead and type them in time. Cleanly typed words light up and are counted as "clean words".

The synthetic demo can also be slowed to 70% or 85% speed.

React + Vite + TypeScript, the native Web Audio API, and Vitest. There is no backend.

```sh
npm install
npm run dev        # http://localhost:5173
npm test           # unit tests (Vitest)
npm run build      # typecheck + production build
npm run beatmap    # regenerate the demo manifest/beat map
```

**Controls:** type the falling keys as they reach the line. Spaces are never judged, so type them or not. Enter starts, Esc pauses and resumes. The game pauses automatically when the tab is hidden.

## Demo song

*Neon Tide* is an original synthetic track (A minor, 100 BPM, 66 s). Its stems are **rendered in your browser at load time** with `OfflineAudioContext`; there are no audio files and no third-party music.

| Stem | Control | Notes |
|---|---|---|
| Voice | auto | Formant-filtered "singer" with vibrato, portamento and reverb. Clearly synthetic. |
| Pulse | auto | Kick, hats, claps; doubles as a metronome. |
| Bass | left hand | One note **per left-hand beat event**, rendered from the beat map. |
| Keys | right hand | One stab/arp note **per right-hand beat event**, rendered from the beat map. |

Because the bass and keys are rendered from the beat map itself, every playable event has a real note on exactly its timestamp. A browser probe measured onsets 1–8 ms after each event, which is just the attack ramp.

The manifest lives at [public/songs/neon-tide/manifest.json](public/songs/neon-tide/manifest.json). It is generated by [scripts/generate-demo-manifest.mjs](scripts/generate-demo-manifest.mjs) and committed as explicit events (`{ "t": 4800, "hand": "left", "instrument": "bass" }`). It holds two charts:

- **Two lanes** (178 events): per-hand word sequences, using only letters that hand types on QWERTY, with exactly one character per event.
- **One sentence** (124 events): *"the tide rolls in under neon light…"*. Letters fall on quarter notes in the verse and eighth notes after, with a rest where each space goes. The generator sets each event's hand from its letter's QWERTY side.

Because the bass and keys are rendered from the chosen chart, the instrument parts differ between modes: the sentence literally becomes the riff. Switching modes re-renders only those two stems. **Speed** rescales `bpm`, `durationMs` and every beat time together and re-renders all stems. Editing `bpm` by hand would desync the voice and pulse, which follow the tempo, from the beat map, which uses absolute times.

## Architecture

```
            ┌──────────── src/song ─────────────┐
manifest ──▶│ validateManifest → buildChart      │──▶ BeatEvent[]  (+ AudioBuffers via loadStems:
            └────────────────────────────────────┘                  url → decodeAudioData, synth → OfflineAudioContext)

keydown ──▶ input/KeyboardInput ──GameKeyInput{hand,char,timeStamp}──▶ game/GameSession ──▶ rhythm/RhythmEngine (match)
                                                                             │   ▲            rhythm/ScoreTracker (rolling scores)
                                                                             │   │            guidance/GuidanceController (bias)
                                                         setStemGain ◀───────┘   └── songTimeAt(perf) ── audio/AudioEngine
                                                                                                          (AudioContext clock)
rAF ──▶ ui/FrameLoop ──▶ session.tick(now) ──▶ canvas lanes, meters, progress   (samples the clock; never defines it)
React ◀── useSyncExternalStore(session.subscribe) ── HUD snapshot (changes only on judgments/state/settings)
```

| Module | Responsibility | Framework-free |
|---|---|---|
| `audio/AudioEngine` | One AudioContext; per stem `source → gain → panner → analyser → master → limiter`. Sample-aligned start, pause/resume/restart, smooth gains, cleanup. | ✓ |
| `audio/clock` | Maps `performance.now()` timestamps to the *heard* context time. | ✓ |
| `audio/synth` | Demo stem generators and offline rendering. | ✓ |
| `rhythm/RhythmEngine` | Deterministic keystroke ↔ event matching and clock-driven misses. | ✓ |
| `rhythm/scoring` | Combo, accuracy, per-instrument rolling score, gain curve. | ✓ |
| `input/*` | QWERTY hand map, key classification, held-key guard, sequence → event characters. | ✓ |
| `guidance/*` | Timing-bias estimator, fixed/adaptive visual cue shift. | ✓ |
| `song/*` | Manifest schema validation, loading, chart building. | ✓ |
| `game/GameSession` | Coordinates the above; exposes snapshots for React and `tick()` for the canvas. | ✓ |
| `ui/textTrack` | Sentence layout in columns, and the column under the cursor at any song time (interpolated between letter beats, so scroll speed follows the rhythm). | ✓ |
| `ui/*` | React presentation; lanes and the sentence stage are canvas drawn from the frame loop. | |

## Timing model

- **One clock.** Song position is always derived from `AudioContext.currentTime`. All stems are started with the same `start(when, offset)`. Neither React state nor `requestAnimationFrame` defines time; the frame loop only decides how often the audio clock is sampled.
- **Heard time, not scheduled time.** A keystroke's `KeyboardEvent.timeStamp` (on the `performance.now()` timeline) is mapped to the context time *being heard* at that moment, using `AudioContext.getOutputTimestamp()`. If that is unavailable, zeroed, or implausible, the fallback is `currentTime − (outputLatency + baseLatency)`. Visuals use the same mapping.
- **Calibration** (−300…+300 ms, saved per browser) is subtracted from that song clock, shifting judgments and visuals together. Raise it if every hit reads late, which is typical with Bluetooth audio, where reported latency is often wrong. "Set from my timing" folds the measured bias into it.
- **Windows:** perfect ±45 ms, great ±90, good ±140. Anything outside ±140 ms cannot match.
- **Misses** are declared from the clock with no input needed, 50 ms after a window closes. That grace period lets key events delivered late by a busy main thread still count.
- **Pause** stops the one-shot sources after a 12 ms fade and remembers the position. **Resume** starts fresh sources at that offset, again all on one `when`.

### Matching rules

1. Only pending events on the keystroke's hand within ±140 ms are eligible. The hand comes from `KeyboardEvent.code` (physical key); the character comes from `KeyboardEvent.key`.
2. Events whose character matches are preferred. Among those, the closest in time wins, with ties going to the earlier event.
3. A keystroke with no character match consumes the closest eligible event as **wrong**. That event cannot be re-hit.
4. A keystroke with no eligible event is an **extra** (stray). It consumes nothing.
5. Each keystroke matches at most one event, and each event is judged once.

Ignored: `repeat` keydowns, IME composition (`isComposing`, `Process`, keyCode 229), Ctrl/Meta/Alt shortcuts, non-character keys (dead keys), keys outside the QWERTY letter/number/punctuation block, and re-presses of a physically held key.

### Mixing

Each instrument keeps an exponential moving average of its judgments (α 0.25; perfect 1, great 0.85, good 0.6, wrong/miss 0). Extra keystrokes nudge the hand's instrument down slightly without breaking combo. The score maps to gain as `0.05 + 0.95·score^1.6`, so the floor leaves a faint ghost of what you're missing. Gain changes use `setTargetAtTime` (τ 50 ms). Auto stems stay at their manifest gain.

### Adaptive guidance

A per-hand estimator keeps the last 16 valid hits (perfect, great or good with the right character). It reports their 20%-trimmed mean once it has 6 samples, clamped to ±60 ms. In **adaptive** mode each lane's cues (keycaps and beat grid) are drawn that many ms earlier or later. In sentence mode the single line of text shifts by the mean of the two hands' estimates. The audio timeline and the scoring windows are never touched. **Fixed** mode still measures and displays the bias.

Bias is measured against true event times, not against the shifted cues. Measuring against the cues would fully correct a player who follows only the visuals. But for anyone who follows the music, it chases its own correction to the bound: a headless play-through with a consistently 25 ms late player ran to 60 ms that way. Measured against true times, the shift equals the player's habit (26–27 ms in the same test) and stays stable. A purely visual player gets about half compensation.

## Song manifest

```jsonc
{
  "version": 2,
  "id": "neon-tide", "title": "Neon Tide", "artist": "…", "bpm": 100, "durationMs": 66000,
  "synthetic": true,                       // optional: generated audio; enables the speed control
  "stems": [
    { "id": "vocals", "label": "Voice", "role": "auto", "source": { "type": "synth", "generator": "neon-tide/vocals" }, "gain": 0.8 },
    { "id": "bass", "label": "Bass", "role": "instrument", "source": { "type": "url", "url": "stems/bass.wav" }, "pan": 0 }
  ],
  "hands": { "left": { "instrument": "bass" }, "right": { "instrument": "keys" } },
  "charts": [
    {
      "id": "two-lanes", "label": "Two lanes",
      "typing": { "mode": "split", "left": "brave waves crest", "right": "jolly moon pony" },
      "beatMap": [ { "t": 4800, "hand": "left", "instrument": "bass" } ]
    },
    {
      "id": "one-sentence", "label": "One sentence",
      "typing": { "mode": "sentence", "text": "the tide rolls in" },
      "beatMap": [ { "t": 4800, "hand": "left", "instrument": "bass" } ]
    }
  ]
}
```

URL stems are fetched relative to the manifest and decoded with `decodeAudioData`. They must all share the same start point.

Validation reports every problem with a path (e.g. `charts[1].beatMap[5].hand: "h" is typed by the right hand`). It checks:

- types and ranges, unique stem and chart ids, and references to instrument stems;
- sorted events within the song duration, with a minimum same-hand spacing;
- for `split`, that each hand's text only uses characters that hand types on QWERTY (texts repeat if shorter than the hand's events);
- for `sentence`, one event per letter, with each event on the hand that types its letter. Only unshifted characters are allowed; capitals are fine because they compare lowercased.

## Adding a song

A recorded song needs three things:

1. **Separate stems.** The mechanic mixes stems, so one full-mix MP3 isn't enough. Provide the best-quality file you have (WAV, FLAC or ALAC; otherwise 320 kbps MP3). Then split it locally with [Demucs](https://github.com/facebookresearch/demucs): `htdemucs_6s` separates vocals, drums, bass, guitar, piano and other. Export WAV stems, so all of them share sample-exact start points (MP3 encoder padding varies by browser).
2. **One instrument per hand.** The vocals become an `auto` stem. If the song is mostly voice and piano, the piano can be split into two instrument stems: a low band for the left hand and a high band for the right. That mirrors how a pianist plays and needs a small crossover-filter source type (not built yet).
3. **A beat map.** Recorded music, especially live, drifts in tempo, so a BPM grid won't line up. The practical route is a tap-along recorder: play the song, tap the rhythm you want to type, save the timestamps (not built yet). Automatic onset detection on the separated piano stem can then refine the taps. A `sentence` chart then lays any text over those taps; typing the actual lyrics would need a timestamp per letter, which is more charting work.

Keep recordings you don't own the rights to out of the repo: put them under `public/songs/local/`, which is gitignored. The app currently loads the demo manifest via `MANIFEST_URL` in `src/App.tsx`; a song picker comes with the first real song.

## Browser limitations and assumptions

- **Autoplay:** the AudioContext is created suspended while stems render and is resumed by the Start click or Enter key.
- **`getOutputTimestamp`** is used where available (Chromium, Firefox) and falls back to reported latency otherwise. Reported `outputLatency` is unreliable on some Bluetooth devices and is missing in older Safari versions; calibration covers the remainder.
- **Input timestamps** assume `KeyboardEvent.timeStamp` is on the `performance.now()` timeline, which is true in all current engines. Implausible values fall back to "now". Keyboard hardware scan latency (often 5–20 ms) is not measured; calibration absorbs it.
- **Display latency** (one or two frames) isn't modelled; adaptive guidance absorbs a constant visual offset.
- **Layouts:** hands are classified by physical position (QWERTY touch-typing split, `code`), and characters are validated by `key`. On AZERTY or Dvorak the hand split is still physical, but the demo words assume QWERTY letters, so other layouts will produce "wrong key" judgments.
- **Memory/CPU:** the demo renders four mono 66 s stems at the context rate (~13 MB each at 48 kHz). That takes about 3 s in parallel on an Apple-silicon laptop and shows a progress label meanwhile.
- **Touch devices** have no physical keyboard; the intro says so.
- **Mobile Safari "interrupted" state** (calls, Siri) is not handled specially. The audio clock stops, so the game freezes consistently rather than drifting.

## Tests

`npm test` runs 85 unit tests:

- **Matching:** grades, inclusive windows, one-to-one matching, character preference, closest candidate, wrong keys, repeated presses.
- **Misses:** clock-driven misses, misses ordered before the keystroke that exposed them, skipped events.
- **Hands:** independence and simultaneous hits.
- **Scoring:** rolling scores and gain mapping, misses lowering scores with no input, combo and accuracy, stray handling.
- **Bias estimator:** minimum samples, trimmed mean, window, bound, stability for audio-following and visual-following players.
- **Input:** key classification (repeat, IME, modifiers, non-gameplay keys, AZERTY), held-key guard, blur, timestamps, split and sentence assignment.
- **Manifest:** validation of the demo and of many invalid manifests (including sentence/hand mismatches), demo-content invariants for both charts, and speed scaling.
- **Audio lifecycle** against a recording fake AudioContext: shared start time and offset, clock-derived position, pause/resume offsets, restart, stale `ended` events, gain smoothing, master fades, disposal, and output-timestamp mapping and fallbacks.
- **GameSession** coordination with a fake audio clock, including the cross-hand next letter in sentence mode and clean-word counting.
- **Text track:** column layout, letters reaching the cursor exactly on their beats, interpolation across rests, and edge extrapolation.

In development, the session is exposed as `window.__typopro` for console poking and automated play-throughs.
